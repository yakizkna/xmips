# Usage Guide for Xmips (Go Reimplementation)

> **Language / 语言**: [中文](USAGE.md) · [English](USAGE.en.md)

This version reimplements the Xmips teaching simulator from *"Xmips Instruction Set and ABC Assembly Language"* in Go. The instruction set, instruction encoding format, and ABC assembly semantics remain consistent with the original version, and are intended for learning instruction sets, assembly language, and operating system principles. The behavior verification examples are `SUM.cupa` and `BUBBLE_INT.cupa`.

## 1. Running

This version has no `Xmips.exe` executable; you must compile it first and then run it:

```bash
./tool.sh build       # compile → install to /usr/local/bin/xmips; sync dist/* to ~/.xmips/; rebuild the system function library
./tool.sh clean       # uninstall: rm -rf ~/.xmips; rm /usr/local/bin/xmips
```

Running (you can call it directly from any directory; the binary is in `/usr/local/bin/xmips` and the data is in `~/.xmips/`):

```bash
xmips                           # A. no argument → run the programs registered in ~/.xmips/run.list
xmips XXX.cupa                  # B. specify a program: current directory first, then ~/.xmips/userfile/
xmips /absolute/path/XXX.cupa   # C. specify an absolute or relative path to a program
xmips update                    # D. rebuild the system function library (re-assemble ~/.xmips/sysfun/*.scp to generate .co)
```

> Note: `config.ini`, `run.list`, `sysfun/`, and `userfile/` are all automatically located in **`~/.xmips/`** (overridable via the environment variable `XMIPS_HOME`), independent of the current working directory, so you can run directly from any directory. Files `open`ed by the user are real host files (relative to the current working directory or an absolute path), so any path on the host can be read or written directly. `xmips` is installed to `/usr/local/bin/xmips` (in PATH), so you can run `xmips XXX.cupa` from any directory.

By default, it runs the programs registered in `run.list` (`run.list` is located at `~/.xmips/`).

## 2. System Directory Layout

The xmips system data directory (`~/.xmips`, synced from the repository `dist/` by `./tool.sh build`) contains:

| Item | Description |
|------|-------------|
| Executable | `/usr/local/bin/xmips` (installed by `./tool.sh build`) |
| Configuration file | `config.ini` (uses built-in defaults when absent) |
| Run list | `run.list` |
| User program directory | `userfile` |
| System program directory | `sysfun` stores the system function library, not modifiable by users |

Regarding the assembly intermediate artifact `.co`: user programs are re-assembled from `.cupa` at runtime, and the `.co` is generated in the **current running directory** and **deleted immediately after loading**; the `.co` of system functions is generated by `./xmips update` and **persistently stored in the `~/.xmips/sysfun/` directory** (loaded directly at runtime for speed), and `./tool.sh clean` clears it together with the entire `~/.xmips/`.

## 3. Path Setup and Parameter Configuration

### 3.1 Path Settings

1. All user assembly source files must be saved in the `~/.xmips/userfile` directory.
2. The run list file `run.list` (located at `~/.xmips/`) registers the names of programs to be assembled and run.
3. ABC assembly source programs have no extension requirement, but `.abc` or `.cupa` is recommended.
4. `run.list` must end with `end`/`END`; content after `end`/`END` will no longer be read.

### 3.2 Parameter Configuration

Configuration parameters are stored in the `~/.xmips/config.ini` file and can be modified by the user. The configurable parameters are as follows:

- **`<1> delayMode` — memory-access delay simulation**

  Because in a real computer accessing main memory is much slower than accessing registers, the Xmips system provides a memory-access delay simulation feature.

  ```ini
  delayMode = 0 ; memory-access delay simulation OFF (exposes the speed difference between memory access and register access at runtime)
  delayMode = 1 ; memory-access delay simulation ON
  ```

- **`<2> displayMode` — display mode (three possible values in this version)**

  ```ini
  displayMode = 0 ; hide process loading content; do not show the source program during assembly
  displayMode = 1 ; show all information; show the source program during assembly
  displayMode = 2 ; only show standard output and system errors; do not ask whether to show the data segment at the end, exit directly
  ```

- **`<3> reportLevel` — system runtime status report level**

  The Xmips system displays runtime status information during operation (assembly syntax errors, interrupt modes, process completion, etc.).

  ```ini
  reportLevel = 0 ; only report Warning and Error
  reportLevel = 1 ; report Normal and Error
  reportLevel = 2 ; report all information
  ```

- **`<4> updateSysfun` — rebuild the system function library (now a standalone command)**

  The system function library provides a set of APIs that users can call via software interrupts; users cannot modify them. System functions are stored as `.scp` source programs in the `~/.xmips/sysfun/` directory; after assembly they generate `.co` character-code files that are **persistently stored in the `sysfun/` directory** and loaded directly at normal runtime for speed. If you modify a `.scp` source program under `sysfun` or delete its `.co`, rebuild the system library with the standalone command:

  ```bash
  xmips update   # re-assemble ~/.xmips/sysfun/*.scp to generate .co
  ```

  This command only rebuilds the system function library and exits; it does not execute any user program.

- **`<5>` memory size parameters**

  ```ini
  codeSize         ; user process code segment length (words)
  dataSize         ; user process data segment length (words)
  stackSize        ; user process stack segment length (words)
  sysfunCodeSize   ; system function code segment length (words)
  sysfunDataSize   ; system function data segment length (words, points to the caller's data segment at runtime)
  sysfunStackSize  ; system function stack segment length (words)
  ```

  When the program you write is large, you can correspondingly increase parameters such as `codeSize`, `dataSize`, and `stackSize`.

- **`<6>` scheduling parameters**

  ```ini
  cycleTimes   ; time slice size: the maximum number of instructions executed per time slice
  pcbNum       ; number of PCBs: the system's maximum number of concurrent processes
  ```

- **`<7> bitMode` — machine word length**

  The machine word length determines the effective bit width and carry behavior of general-purpose registers and integers in memory, affecting the overflow wrap-around of arithmetic operations such as `ADD/SUB/MUL` and the operation width of `SHL/SHR/ROL/ROR` shifts/rotates.

  ```ini
  bitMode = 64   ; 64-bit integers (default). Values are treated as 64-bit signed integers; overflow does not wrap around
  bitMode = 32   ; 32-bit integers. Arithmetic overflow wraps around by 2^32 (equivalent to C's int);
                 ; SHL/SHR/ROL/ROR operate at 32-bit width
  ```

- **`<8> dump` — per-instruction execution dump log (debugging)**

  When enabled, registers (`#0~#16`) and data-segment memory that changed **in each clock cycle (after each instruction is executed and written back)** are appended to `log/dump.log` in the running directory, in a format such as `[cycle=10 PID=50 PC=213] #6=1 #15=1 m0=4`.

  ```ini
  dump = 0  ; OFF (default)
  dump = 1  ; ON - write the dump log to log/dump.log in the running directory
  ```

**`config.ini` file format requirements:**

1. Each line must not contain spaces; for example, there must be no space between `=` and the parameter value.
2. It must end with `end` (content after `end` is no longer read).
3. Lines starting with a semicolon (`;`) are comment lines; inline comments can also be added after a parameter value using a semicolon (`;`).

## 4. System Function Conventions

System functions: the `.scp` system functions under the `dist/sysfun` directory are named `INT_xx.scp` (xx is the system call number). Currently only INT 10 (bubble sort) uses a `.scp` system function:

```
INT_10.scp  INT 10 system call: bubble sort (uses #11, #12).
```

> INT 13 (output string), INT 14 (standard input), and INT 15~18 (file/Socket) are all executed natively by the dispatcher (no `.scp`, no PCB occupied), so no sysfun directory source file is needed.

The system call numbers are kept consistent with the registers they use for easy memorization:

```
INT 10  uses #11, #12
INT 13  uses #11 (string start address)
INT 14  uses #12 (buffer size), #11 (buffer start address) → return flag is placed in #13 (#13=0 EOF, #13=1 buffer full)
```

- INT 14 (native in the dispatcher) reads characters one by one from stdin into the buffer until EOF is reached or the buffer is full; it returns `#13=0` (EOF) or `#13=1` (buffer full). If interactive return-to-newline input is required, read 1 character at a time (`#12=1`) in the user program and check for Enter yourself (see `GREET.cupa`).
- Note: the input register `#14` must not be read by the user program; reading it triggers the system error `RES=198` (illegal access). User programs should obtain input indirectly from stdin via INT 14.

### File and Real Network Socket (INT 15~18, natively executed by the dispatcher, no `.scp`)

Calling convention: `#10`=call number, `#11/#12`=parameters, and fd is passed in `#9` (the return value is also in `#9`).

| Call no. | Function | Inputs | Return `#9` |
|----------|----------|--------|------------|
| 15 | open | `#11`=path string address (0-terminated in the data segment), `#12`=mode | fd |
| 16 | read | `#11`=buffer address, `#12`=max length, `#9`=fd | number of bytes actually read (0=no data yet/EOF) |
| 17 | write | `#11`=buffer address, `#12`=length to write, `#9`=fd | number of bytes actually written |
| 18 | close | `#9`=fd | — |

Prefixes for the `open` path:

- `sock:host:port`: TCP client; port 443 automatically enables TLS (the cupa does not need to care about encryption).
- `tlssock:host:port`: TCP client; forces TLS (ServerName=host).
- Anything else: a file, mapped to a real host file (relative to the current working directory or an absolute path), so any path on the host can be read or written directly.

`#12` modes: `0`=read-only, `1`=write (truncate), `2`=read-write append (file only). fd starts at 3.

**Blocking semantics** are determined by the single-process mode (`./xmips xxx.cupa` direct run, or `run.list` containing exactly 1 file):

- Single process: socket read blocks and waits, protected by the `sockTimeout` (default 2000ms) timeout; it returns 0 on timeout and does not hang.
- Multi-process: socket read is non-blocking; when there is no data it returns 0 and yields the time slice (placed at the tail of the ready queue to avoid busy spinning).

Socket write and connect/handshake are also governed by `sockTimeout`.

Error codes:

| Error code | Meaning |
|------------|---------|
| -1 | open failed / illegal path |
| -2 | illegal fd |
| -3 | connection failed |
| -4 | write buffer full |
| -5 | socket closed / read/write error |

Example: `userfile/NETTOUR.cupa` (HTTPS fetch `https://ace.yakidev.top/tour` and write it to `tour.html`).

Configuration items: `sockTimeout` (socket timeout in milliseconds); `diskRoot` is a reserved item (no longer forcibly restricting the disk directory).

## 5. Editing Assembly Source Programs

User source programs to be run must be created under the `dist/userfile` directory.

1. An assembly source program must end with an `END` statement.
2. After saving the source program, register the source program name to be run in the `run.list` file.
3. Re-run the program following *"1. Running"* to assemble and execute it.

### 5.1 Function Calls (CALL/RET)

Xmips implements subroutine calls via `CALL` / `RET` (no stack frame, no local variables; parameters are passed by register convention):

- `CALL 标签`: pushes the return address PC and the flag onto the stack, then jumps to the target; `RET` pops the stack to restore.
- Parameters are passed via registers (e.g., `#0`=array start address, `#1`=length), and return values are also stored by convention.

Because code begins executing at address 0 and the assembler terminates at the first `END`, programs with subroutines must follow these rules:

| Constraint | Approach |
|------------|----------|
| Execution entry is at code[0] | The main program must be placed at the very front of the file (after DIM) |
| Assembly terminates at the first `END` | There can be only one `END` in the whole file, and it must be at the end |
| The main program must not fall through into a subroutine | End the main program with `HALT` (`HALT` is equivalent to `END` for normal termination, but does not stop assembly) |
| Label syntax | Must be `: name` (colon prefix); `name:` reports `RES=14` |
| Subroutine references | `CALL` may forward-reference a label defined later (like forward jumps, patched in two passes) |

See the example in `userfile/BUBBLE_CALL.cupa` (two user subroutines: `CALL BUBBLE` bubble sort and `CALL PRINUM` number output).

### 5.2 Notes

- `DIV 寄存器, 10` writes the **remainder into `#0`**; if the dividend target happens to be `#0`, the quotient will be overwritten by the remainder, causing an infinite loop. You need a separate working register (see `PRINUM` in `BUBBLE_CALL.cupa`, which uses `#8` as a copy of num).

### 5.3 MD5 Calculator (`userfile/MD5.cupa`)

- Requires `bitMode=32` (see config 3.3). Content from standard input → outputs a 32-digit lowercase hexadecimal MD5.
- **Input limit of 448 bytes** (single-block implementation, leaving a 64-bit length field):
  - For content of **≤448 bytes**, the result **exactly matches** the system `md5` command (including binary data containing `0x00`).
  - For **overlong** content, only the beginning is computed, and the result differs from `md5` — this is expected, not a bug.
- Usage: `./xmips < file` (reads content from stdin and computes).

```bash
$ printf 'hello file test 123' > t.txt
$ md5 -q t.txt           74fa1393381c99b2fd446ef775aca3a6
$ ./xmips < t.txt        74fa1393381c99b2fd446ef775aca3a6
```
